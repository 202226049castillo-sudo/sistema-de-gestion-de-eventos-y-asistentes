# cybersecurity_implementations.md

## 🛡️ Informe de Implementaciones de Ciberseguridad

Este documento técnico describe a detalle cada una de las capas de seguridad integradas en el ecosistema del software, abarcando desde la protección a nivel de hardware/navegador hasta la seguridad en el almacenamiento de base de datos. Cada medida ha sido diseñada para mitigar vectores de ataque específicos como XSS, SQL Injection, DoS y filtración de datos.

---

## 1. Conceptos y Definiciones

A continuación se detallan las tecnologías y metodologías aplicadas en el código fuente, explicando su funcionamiento interno:

* **Cifrado Autenticado AES-GCM (Advanced Encryption Standard - Galois/Counter Mode):** Implementado en `app.js` mediante la Web Crypto API. A diferencia del cifrado estándar, GCM no solo garantiza la **confidencialidad** (que nadie lea el dato), sino también la **integridad** (que el dato no haya sido alterado). Utiliza un Vector de Inicialización (IV) de 12 bytes generado aleatoriamente para cada operación, asegurando que el mismo texto cifrado dos veces produzca resultados diferentes, frustrando ataques de diccionario o análisis de patrones.
* **Derivación de Claves PBKDF2 (Password-Based Key Derivation Function 2):** Referenciado en la configuración de `app.js` con 100,000 iteraciones. Este concepto se basa en el estiramiento de claves (key stretching), lo que eleva el costo computacional para un atacante que intente realizar ataques de fuerza bruta, haciendo que el descifrado sea inviable en términos de tiempo y recursos.
* **Política de Seguridad de Contenido (CSP) y Seguridad de Cabeceras vía Helmet:** Implementado en `index.js`. Helmet actua como un middleware que configura automáticamente cabeceras como `Content-Security-Policy`, la cual restringe las fuentes desde las cuales el navegador puede cargar scripts, estilos o imágenes. Esto es la defensa definitiva contra la ejecución de scripts no autorizados que intenten robar cookies de sesión o tokens.
* **Sanitización y Escapado de Salida (Output Escaping):** En `guardar_asistente.php` y `app.js` se utiliza la técnica de transformar caracteres peligrosos (como `<` o `>`) en entidades HTML seguras. En el frontend, el uso de `textContent` en lugar de `innerHTML` garantiza que cualquier cadena recibida del servidor sea tratada estrictamente como texto plano, neutralizando cualquier intento de ataque XSS (Cross-Site Scripting) persistente o reflejado.
* **Control de Concurrencia mediante Bloqueo Exclusivo (Locking):** En `conexion.php`, la función `guardarJSON` utiliza el flag `LOCK_EX`. Este concepto de seguridad operativa evita condiciones de carrera (Race Conditions), donde dos escrituras simultáneas podrían corromper la integridad del archivo de datos, resultando en una denegación de servicio lógica o pérdida de registros críticos.
* **Validación Estricta de Esquemas con Express-Validator:** En `eventos.routes.js`, se implementa la validación a nivel de ruta. No solo se verifica que el dato llegue, sino que cumpla con un esquema: que el ID sea alfanumérico, que la fecha sea formato ISO8601 y que la capacidad sea un entero positivo. Esto evita que datos malformados lleguen a la lógica de negocio, protegiendo contra desbordamientos o errores inesperados del motor.

## 2. 10 Ventajas Estratégicas del Modelo de Seguridad

1.  **Protección Profunda (Defense in Depth):** La mayor ventaja es que el sistema no depende de una sola medida. Si el cifrado en el frontend fallara, el sistema cuenta con sanitización en el backend, límites de carga en el servidor y roles restringidos en la base de datos, creando múltiples muros para el atacante.
2.  **Mitigación de la Denegación de Servicio (DoS):** Gracias a los límites de tamaño en `php://input` y en el middleware de Express (`limit: '10kb'`), el servidor es inmune a ataques que intentan agotar la memoria RAM mediante el envío de archivos o cadenas de texto extremadamente largas.
3.  **Cumplimiento de Privacidad y Normativas (GDPR/LFPDPPP):** El uso de `VARBINARY` para correos y teléfonos en `bd.sql`, junto con el cifrado AES-256 en reposo (`ENCRYPTION='Y'`), asegura que la empresa cumpla con las leyes internacionales de protección de datos personales.
4.  **Aislamiento de la Lógica del Servidor:** Al incluir validaciones que impiden el acceso directo a archivos (como en `conexion.php` comprobando el `SCRIPT_FILENAME`), se evita que un atacante pueda ejecutar scripts internos llamando directamente a las rutas de archivos de soporte.
5.  **Garantía de Origen y Control de Acceso:** La implementación de CORS (Cross-Origin Resource Sharing) en `index.js` asegura que solo el dominio autorizado (ej. el puerto 5500 local o el dominio de producción) pueda consumir la API, bloqueando peticiones maliciosas desde otros sitios web.
6.  **Reducción del Riesgo de Clickjacking:** El uso de la cabecera `X-Frame-Options: DENY` en todos los archivos PHP garantiza que la interfaz de la aplicación no pueda ser embebida en marcos ocultos de otros sitios, evitando que los usuarios realicen acciones involuntarias.
7.  **Integridad de Datos en Tránsito:** Al forzar `REQUIRE SSL` en los usuarios de la base de datos creados en `bd.sql`, se garantiza que toda comunicación entre el servidor web y la base de datos viaje cifrada, impidiendo ataques de "Man-in-the-Middle".
8.  **Depuración Segura:** El manejo centralizado de errores en `index.js` y los bloques `try-catch` en PHP ocultan el *stack trace* (rastreo de error) al usuario final, enviando solo mensajes genéricos. Esto evita que el atacante conozca la estructura de directorios o versiones de software.
9.  **Prevención de MIME Sniffing:** Mediante la cabecera `X-Content-Type-Options: nosniff`, se obliga al navegador a respetar estrictamente el tipo de contenido enviado (JSON), impidiendo que archivos de texto sean interpretados como scripts ejecutables.
10. **Trazabilidad y Auditoría Post-Incidente:** El registro de la dirección IP (`REMOTE_ADDR`) en la creación de eventos permite a los administradores realizar análisis forenses en caso de detectar comportamiento anómalo o registros fraudulentos.

## 3. 10 Casos de Uso y Escenarios de Ataque

1.  **Ataque de Inyección de Scripts en Comentarios:** Un atacante intenta registrarse como asistente usando el nombre `<img src=x onerror=alert(1)>`. Gracias a `htmlspecialchars` y `strip_tags` en `guardar_asistente.php`, el script es destruido antes de guardarse, y al mostrarse en `app.js`, el uso de `textContent` renderiza la cadena como texto inofensivo en lugar de ejecutar la imagen.
2.  **Intento de Escalada de Privilegios en Base de Datos:** Un usuario malintencionado logra acceso a la consola de la base de datos. Al intentar consultar la tabla de asistentes, solo ve datos binarios ilegibles en la columna `correo` debido al cifrado AES-256. Sin la clave simétrica protegida, la información es inútil para el atacante.
3.  **Ataque por Fuerza Bruta de Carga de Datos:** Un bot intenta enviar miles de peticiones POST con objetos JSON de 10MB para saturar el servidor. El middleware `express.json({ limit: '10kb' })` en `index.js` corta la conexión inmediatamente al detectar que el tamaño excede el límite permitido, manteniendo el servicio disponible para otros usuarios.
4.  **Acceso no Autorizado desde Sitios Externos:** Un competidor crea una página web que intenta hacer peticiones `fetch()` a tu endpoint `/api/eventos` para robar tu base de datos. El navegador bloquea la petición porque el dominio del competidor no está incluido en la lista blanca de la configuración `CORS`.
5.  **Secuestro de Sesión mediante Iframes (Clickjacking):** Un atacante crea un sitio web de premios falsos y pone tu formulario de registro en un iframe transparente encima de un botón de "Reclamar Premio". Sin embargo, el navegador del usuario se niega a cargar tu sitio dentro del iframe debido a la cabecera `X-Frame-Options: DENY`.
6.  **Corrupción de Base de Datos por Escritura Simultánea:** Durante un evento masivo, 100 personas intentan registrarse en el mismo segundo. Sin el bloqueo `LOCK_EX` en `conexion.php`, el archivo JSON podría quedar a medias o borrarse. Con el bloqueo, el sistema operativo encola las peticiones, procesando cada una de forma atómica y segura.
7.  **Inyección de Parámetros Malformados en URL:** Un atacante intenta acceder a `eventos/../config/settings` para realizar un ataque de Path Traversal. El validador `param('id').isAlphanumeric()` en `eventos.routes.js` detecta los puntos y barras como caracteres no permitidos y rechaza la petición con un error 400 antes de que toque el sistema de archivos.
8.  **Robo de Credenciales en Redes Wi-Fi Públicas:** Un administrador intenta conectarse a la base de datos desde una cafetería. Si no hubiera `REQUIRE SSL` en `bd.sql`, un atacante en la misma red podría "oler" el tráfico. Gracias a esta regla, la conexión no se establece a menos que sea a través de un túnel cifrado TLS/SSL.
9.  **Ataque de MIME Sniffing con Archivos "Disfrazados":** Un atacante logra subir un archivo de texto que contiene código JavaScript, esperando que el navegador lo ejecute. La cabecera `nosniff` configurada en todos los archivos PHP le indica al navegador que no intente adivinar el tipo de contenido y lo trate estrictamente como el JSON que el servidor declara.
10. **Agotamiento de Recursos por Peticiones GET Masivas:** Un usuario malintencionado intenta descargar todo el catálogo de eventos repetidamente. Las validaciones de entorno en `asistentes.php` (Nivel 2) y el manejo de errores controlado (Nivel 3) aseguran que el sistema responda con códigos HTTP apropiados (404/500) y registre el error en los logs internos, permitiendo al firewall del servidor bloquear la IP sospechosa automáticamente.
